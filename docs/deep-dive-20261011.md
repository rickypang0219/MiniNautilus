## Measurement and fsync

Merged `claude/inspiring-lamport-u2zx1j` at `3320155` and applied its verification/evidence workflow. `ops/compare.py` requires at least five successful compatible runs per side, non-overlapping ranges and at least 10% median effect. Single-run changes remain inconclusive.

`MINI_ORDER_TRACE=/new/path/orders.jsonl` enables request IDs and action traces for SendOrder/SendCancel: journal, sequence, order ID, Python request/decision timing, Rust prepare/encode/write/sync/commit timings, bytes written and bytes pending the foreground sync. Rust trace timing stops before response serialization. Python receipt does not prove venue delivery. The Testnet SMA runtime separately records `order_delivery` with matching request/order IDs and REST acknowledgement status. Soak enables tracing for each run; logging overhead is present in every compared soak.

A/A: the same clean commit and binary, five interleaved runs per side, fixed seed 7, 1,200 observations at 100 Hz. Tick-to-trade p99 spans 3.33–17.92 ms across identical runs; all comparison verdicts are inconclusive. Final orders, fills, cash and position match in every run.

Prototype `c191651`: a background sync every 5 ms or 32 KiB, with conservative acknowledgement of the prefix observed before sync, sticky background errors, and an unchanged foreground fsync before every external action. Verification and recovery tests passed. Five repetitions gave tick-to-trade p99 median 6.53 ms (5.08–9.32), versus baseline 5.29 ms (3.33–11.07). Rust request timing was likewise inconclusive. The prototype was reverted in `73c2361`.

The perf-investigation skill says: “Keep the change only if the target metric is `improved` and nothing it touches is `regressed`. `inconclusive` means no claim: raise reps or revert.” Source: `.claude/skills/perf-investigation/SKILL.md`.

Correlated evidence: in the slowest 1% of order requests, median fsync time was 99.25% of Rust pre-response processing time. Action-frame encoding was only 3.52 microseconds. Background sync reduced median pending bytes from 1,004.5 to 793, and the maximum from 15,279 to 3,122, without establishing a latency benefit. Offline re-encoding of one 7,863-frame sample as an inline JSON object would save only 8.25% of total bytes; this is a size calculation, not a runtime benchmark. No journal format migration was shipped.

**The <=5 ms tick-to-trade goal is not met.** The next useful performance experiment is the same fixed-input workload on the intended EC2/EBS filesystem, followed by a storage/commit policy experiment that preserves the external-effect barrier. A noisy shared container cannot certify that deployment target.

Crash guarantees are unchanged: every-input sync remains the default; Outbox syncs the causal input and all earlier writes before exposing SendOrder/SendCancel. Unsynced market-only suffixes can be lost on OS/storage failure. Recovery replays without dispatch and gates trading until reconciliation. Power-loss hardware testing was not performed.

## Synthetic driver and rotation

Synthetic market observations now use one timestamp and one send_batch for Tick, Heartbeat, QuoteObserved and two Trades. `--unbatched` retains the five-call reference with identical event generation. A parity test compares effects, every intermediate state and fills over 500 deterministic updates. Quotes are bounded above zero even when the random walk reaches its lower limit.

`--rotate-orders N` is opt-in. At >=N retained orders, rotation waits for Healthy, flat inventory and no open/uncertain orders. It syncs/closes the old journal, creates a carried successor, recovers gated, reconciles a fresh paper venue and returns a full Python mirror. Cash, kill latch, epoch/target revision and the client-order ID floor survive. It does not liquidate to force a rotation. `--long-only` provides natural flat opportunities in synthetic sessions. N is a soft trigger, not a hard memory limit.

Automatic in-process rotation is restricted to durable paper sessions. Live rotation still requires coordinated adapter recovery/reconciliation; resetting a live venue is never inferred from local flat inventory. Existing offline rotation remains available. TTL bookkeeping now retains only open orders.

`system.jsonl` records Linux process RSS/high-water marks, scheduler run/wait counters, context switches, process I/O, host pressure and cgroup CPU/I/O counters. Missing measurements remain missing. A rising last/first p99 ratio is a FAIL signal, not proof that history caused the rise.

Five interleaved 30-second repetitions per variant (200 updates/s, SMA 5/20, candle every two updates, long/flat, seed 7, Outbox, tracing enabled) found:

- Market IPCs per update: 5 to 1, improved (80% fewer).
- Loop p99 median: 4.302 ms [4.066, 9.770] to 3.304 ms [2.845, 3.751], improved under the five-run rule.
- Overruns per 1,000 updates: median 5.194 [3.346, 42.584] to 2.677 [2.001, 3.691], inconclusive because ranges overlap.
- Tick-to-trade: inconclusive. Rust-request/IPC quantiles are not comparable across batch sizes because the unit of work per request changed. Absolute acceptance FAILs are retained.
- Rotation at 25 retained orders completed five times in each short run, with every run Healthy. No latency improvement is claimed for rotation.

The short runs exposed an existing report bug: the drift query started after its end for windows under 60 seconds. The raw reports retain that diagnostic query error; independently successful latency queries and exact driver counts are unchanged. Reporting now returns NO DATA unless at least two complete drift slices exist.

The first sustained rotation run lasted 10 minutes: 118,700 updates, 2,203 cumulative orders, 2,843 fills, 21 rotations, 85 retained orders at shutdown. Rust RSS rose from 2,412 to 8,884 KiB and then plateaued for the final three time slices. Rotation replays whole predecessor journals, producing an allocator high-water cost. Python RSS kept rising from 33,544 to 36,860 KiB despite bounded engine history.

That Python growth revealed a second cause: `SmaTarget.prices` retained every observation. It now uses an O(slow) fixed-size ring with O(1) updates. A failing-before test confirms that the old implementation retained nine prices with an eight-price window. Five repetitions of 100,000 streamed prices retained 4,001,792–4,001,824 bytes before versus 1,216–1,248 bytes after, with identical hashes of every emitted signal. This allocation result isolates the strategy; it is not a whole-process RSS measurement. A second matched 10-minute soak is being collected before closing the memory investigation.
